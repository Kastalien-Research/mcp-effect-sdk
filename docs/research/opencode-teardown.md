## 0. The single most important structural fact: this repo is mid-rewrite

OpenCode contains **two complete agent stacks running side by side**:

|                         | **V1 (shipping)**                                                       | **V2 (in progress)**                                                                                 |
| ----------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Agent loop              | `packages/opencode/src/session/prompt.ts` (1631 lines)                  | `packages/core/src/session/runner/llm.ts` (432 lines)                                                |
| Provider access         | Vercel AI SDK `streamText` (`packages/opencode/src/session/llm.ts:280`) | own HTTP protocol clients (`packages/llm/src/protocols/*`)                                           |
| Persistence             | `message` + `part` tables (`packages/core/src/session/sql.ts:68-98`)    | event-sourced, `session_message` + `event` (`sql.ts:119-138`, `packages/core/src/event/sql.ts:4-25`) |
| Wire protocol           | hand-rolled routes + OpenAPI → hey-api SDK                              | `HttpApi` contract → generated Effect client                                                         |
| Tool interface          | `packages/opencode/src/tool/tool.ts:56-68`                              | `packages/core/src/tool/tool.ts:39-64`                                                               |
| Permissions             | in-memory approvals (`packages/opencode/src/permission/index.ts`)       | SQLite-persisted (`packages/core/src/permission.ts`)                                                 |
| MCP                     | `packages/opencode/src/mcp/` (1004 lines)                               | **not ported** — no MCP module in `packages/core`                                                    |
| Bash permission parsing | tree-sitter AST (`packages/opencode/src/tool/shell.ts:309-330`)         | **not ported**, regex, self-described "advisory only" (`packages/core/src/tool/bash.ts:66-68, 113`)  |
| Edit fuzzy repair       | 9-replacer cascade (`packages/opencode/src/tool/edit.ts:217-737`)       | **not ported**, exact-match only (`packages/core/src/tool/edit.ts:84`)                               |

This is enormously valuable to us: **V2 is OpenCode's second attempt at the same
product, written by people who had already shipped V1 and knew exactly what
hurt.** Where V1 and V2 disagree, V2 is the considered opinion. Where V2 has a
`TODO: port from V1`, that subsystem was hard enough that they shipped without
it rather than rush it.

The rest of this document reads V2 as the design signal and V1 as the
feature-completeness reference.

## 1. How deeply Effect-based is it?

**Answer: deeply and idiomatically, on Effect 4.0.0-beta.83 (the v4 line, not
v3).**

Effect-file density per package (files importing `effect` / total TS files):

| Package                                     | Ratio   | Verdict                                                  |
| ------------------------------------------- | ------- | -------------------------------------------------------- |
| `core`                                      | 366/477 | idiomatic — services, layers, fibers, streams, Schema    |
| `opencode`                                  | 411/668 | idiomatic (V1 stack, plus CLI)                           |
| `protocol`                                  | 23/24   | pure Effect `HttpApi` + Schema, zero runtime             |
| `llm`                                       | 67/105  | idiomatic — `Stream`, `HttpClient`, Schema-typed events  |
| `schema`                                    | 51/71   | Effect Schema only                                       |
| `server`                                    | 27/29   | `HttpApiBuilder` layers                                  |
| `codemode`                                  | 18/33   | idiomatic values, **no services/layers at all**          |
| `effect-drizzle-sqlite`                     | 14/22   | vendored fork of drizzle's unreleased Effect adapter     |
| `tui`                                       | 8/204   | incidental — SolidJS + OpenTUI, Effect only at the seams |
| `sdk`                                       | 0/44    | generated by hey-api, deliberately Effect-free           |
| `app`, `ui`, `web`, `console`, `session-ui` | ~0      | web frontends, no Effect                                 |

### 1.1 They are on Effect v4, and they patch it

`package.json:60` pins `effect: 4.0.0-beta.83`, with `@effect/platform-node`,
`@effect/sql-sqlite-bun`, and `@effect/opentelemetry` all at matching betas
(`package.json:23-25`). Services use the v4 `Context.Service` form:

```ts
export class Service extends Context.Service<Service, Interface>()(
  "@opencode/v2/SessionExecution"
) {}
```

(`packages/core/src/session/execution.ts:22`)

They carry a patch **against Effect itself** —
`patches/effect@4.0.0-beta.83.patch`, 57 lines, fixing `HttpApiSchema.StreamSse`
so the JSON-string SSE wrapper gets its own OpenAPI identifier
(`${identifier}Stream`) instead of stealing the decoded data schema's name. This
is a real signal: **the v4 HttpApi/SSE surface is not yet finished**, and a
serious user hits its edges within weeks.

### 1.2 The custom DI layer: `LayerNode`

`packages/core/src/effect/layer-node.ts` (333 lines) is a **typed
dependency-graph wrapper over `Layer`**. A node bundles a service tag, its
layer, and its declared dependency nodes, and the type system rejects a node
whose layer requires a service not present in its `deps`:

```ts
type Missing<Required, Dependencies extends NodeList> = Exclude<
  Required,
  Output<Dependencies[number]>
>
type CheckDependencies<
  Implementation extends Layer.Any,
  Dependencies extends NodeList
> = [Missing<Layer.Services<Implementation>, Dependencies>] extends [never]
  ? unknown
  : {
      readonly "Missing dependencies": Missing<
        Layer.Services<Implementation>,
        Dependencies
      >
    }
```

(`layer-node.ts:10-14`)

Usage at the bottom of every service module — e.g. the session runner declares
all 13 of its dependencies as nodes
(`packages/core/src/session/runner/llm.ts:414-432`). There is also a **scope-tag
system** (`LayerNode.tags`, `:57-67`) that partitions nodes into scopes like
`global` vs `location`, and `LayerNode.unbound` for a tag that will be supplied
later (`packages/core/src/session/execution.ts:24`).

This exists because plain `Layer.provide` chains stop being legible past ~50
services, and because OpenCode needs **per-location (per-project-directory)
service instances inside one process** — `makeLocationNode`
(`packages/core/src/effect/app-node.ts`) builds the location-scoped subgraph.
Judgement: this is real engineering, not ceremony, but it is ~330 lines of
type-level machinery we should only adopt if we hit the same multi-instance
requirement.

### 1.3 Where Effect is used well

- **Fibers for tool parallelism** — `FiberSet` per turn, one fiber per tool call
  (`runner/llm.ts:184, 271`).
- **`Deferred` for human-in-the-loop suspension** — the entire permission system
  (`packages/opencode/src/permission/index.ts:98-106`).
- **`Stream` end-to-end** — provider bytes → SSE frames → typed `LLMEvent`s
  (`packages/llm/src/route/client.ts:284-293`) and server → client
  (`packages/server/src/handlers/event.ts:20-48`).
- **`Effect.fn("Name")` everywhere**, which auto-creates a span; this is how
  they get tracing coverage almost for free (see §9).
- **`Cause` discipline** — interruption is consistently distinguished from
  failure via `Cause.hasInterrupts` / `Cause.hasInterruptsOnly` rather than
  being flattened (`runner/llm.ts:295, 303-304, 343`).
- **Schema as the only boundary type** — wire protocol, config, DB rows, tool
  params, and LLM events are all Effect Schema.

## 2. The agent loop

### 2.1 Where it lives

V2: `packages/core/src/session/runner/llm.ts`. Read it — it is the best 430
lines in the repo and the closest thing to a reference implementation of
"durable agent loop in Effect."

Three nested loops:

1. **`run`** (`:383-406`) — outer drain. `while (shouldRun)` over queued inputs;
   inner `while (needsContinuation)` over steps. After each turn it re-checks
   for pending _steer_ input and continues if present.
2. **`runTurn`** (`:369-381`) — one provider turn, wrapped in a defect-catching
   recursion that implements compaction re-entry.
3. **`runTurnAttempt`** (`:173-348`) — assemble request → stream → settle tools
   → publish.

### 2.2 Tool dispatch and parallelism

Tool calls are dispatched **from inside the stream consumer**, eagerly, as the
provider emits them — not batched at end-of-step:

```ts
Stream.runForEach((event) => Effect.gen(function* () {
  ...
  if (event.type !== "tool-call" || event.providerExecuted) return
  needsContinuation = true
  const assistantMessageID = yield* publisher.assistantMessageID(event.id)
  yield* Effect.uninterruptibleMask((restore) =>
    restore(toolMaterialization.settle({ sessionID, agent, assistantMessageID, call: event }))
      .pipe(Effect.flatMap((settlement) => publish(LLMEvent.toolResult({...}))))
  ).pipe(FiberSet.run(toolFibers))
}))
```

(`runner/llm.ts:233-271`)

So: **N tool calls in one assistant step run as N concurrent fibers**, and the
turn ends when `awaitToolFibers` (`:141-142`,
`Effect.raceFirst(FiberSet.join, FiberSet.awaitEmpty)`) drains them. The
`uninterruptibleMask(restore)` wrapper is deliberate — the _recording_ of the
tool call is uninterruptible, the _execution_ is interruptible.

Tools are resolved per step through `tools.materialize(agent.info?.permissions)`
(`:203`), which returns both the model-facing `definitions` and a `settle`
dispatcher (`packages/core/src/tool/registry.ts:24-31, 106-118`). Permission
filtering happens at materialization, so a denied tool is never advertised.

### 2.3 Sub-agents

V1 only (`packages/opencode/src/tool/task.ts`). A subagent is a **child
session** (`parentID`, `packages/core/src/session/sql.ts:31`) run through the
same prompt loop with a derived permission set
(`deriveSubagentSessionPermission`). Notable details:

- **Depth-limited**, default 1, walked by following `parentID` upward
  (`task.ts:104-118`).
- **Background mode** behind `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS`
  (`task.ts:96-100`); returns immediately and notifies on completion.
- **Resumable** via `task_id`, which reuses the prior subagent session
  (`task.ts:50-53`).
- Results are wrapped in `<task id state>` XML for the parent model
  (`task.ts:66-78`).
- The prompt text for background mode is mostly _don't poll me_ discipline
  (`:31-40`).

There is **no sub-agent support in V2 yet** — `runner/llm.ts:63` still lists
tool resolution for plugin/MCP tools as unchecked.

### 2.4 Interruption and steering — the best idea in the codebase

Steering is **durable, not in-memory**. A user prompt arriving mid-turn is
written to a `session_input` table with a `delivery` discriminator of
`"steer" | "queue"` (`packages/core/src/session/sql.ts:140-166`), admitted
through an event (`SessionEvent.PromptAdmitted`,
`packages/core/src/session/input.ts:41-79`). The loop then:

- At the start of each turn, promotes pending steers into the transcript and
  **resets the step counter to 1** (`runner/llm.ts:187-196`), so steering
  refreshes the agent's budget.
- After a turn completes with no tool calls, checks for pending steers before
  exiting (`:401`).
- After the step loop exits, checks for queued inputs and starts a fresh loop
  (`:403-404`).

Concurrency is managed by `SessionRunCoordinator`
(`packages/core/src/session/run-coordinator.ts`, 104 lines) — a per-key
serializer with three operations: `run` (start or **join** the active
execution), `wake` (register one _coalesced_ follow-up), `interrupt` (stop and
await cleanup). The coalescing is the subtle part: multiple `wake`s during a
drain collapse to a single successor run (`:52-63`), so a burst of user input
doesn't spawn a burst of turns.

Interruption itself is Effect fiber interruption
(`Fiber.interrupt(entry.owner)`, `run-coordinator.ts:100`), and the loop
converts it into durable state: unsettled tool calls are marked failed with
`"Tool execution interrupted"` (`runner/llm.ts:299, 307`), and any orphaned
`pending`/`running` tool rows from a _previous crashed process_ are failed at
the start of the next run (`failInterruptedTools`, `:119-139`).

V1 by contrast bridges Effect interruption to an `AbortController` for the AI
SDK (`packages/opencode/src/session/prompt.ts:815-827`,
`Effect.onInterrupt(() => Effect.sync(() => controller.abort()))`).

### 2.5 Compaction re-entry via thrown defects

When the turn needs to restart after compaction, the loop **throws a
`TurnTransitionError` as an Effect defect** and catches it in the recursive
wrapper (`runner/llm.ts:152-166, 355-381`). Two tags: `ContinueAfterCompaction`
and `ContinueAfterOverflowCompaction`, and the post-overflow path explicitly
refuses to recover a second overflow (`:361`).

This is clever but it is **the one place in the file where I'd do it
differently**: a defect is being used as control flow across a typed boundary,
which means the error channel doesn't document a legal outcome of the function.
A `Effect.Effect<Turn.Result | Turn.Restart, ...>` return would say the same
thing in the types.

## 3. `packages/codemode` — the most directly relevant package

**What it is:** an _owned, tree-walking JavaScript interpreter written in
TypeScript_, running Effect. `packages/codemode/package.json:5` describes it as
"Effect-native confined code execution over schema-described tools."

**It is not a sandbox in the Cloudflare sense.** There is no `eval`, no
`new Function`, no `node:vm`, no Worker, no subprocess — grep across
`packages/codemode/src` returns zero hits for all of them. Isolation comes from
the fact that _the interpreter simply has no way to name anything that wasn't
seeded_.

### 3.1 Pipeline

1. Model code is wrapped in `async function __codemode__() { ... }` and passed
   through TypeScript's `transpileModule` — **type-stripping only, no type
   checking** (`src/interpreter/runtime.ts:116-127`).
2. The stripped body is parsed by **acorn**, parse-only, no rewriting or static
   analysis (`:136-143`).
3. `class Interpreter<R>` walks the AST, each node evaluating to
   `Effect.Effect<StatementResult, unknown, R>` (`:602, 778`). The model's
   `await` becomes a genuine Effect bind.

Unsupported syntax is rejected **lazily, at evaluation time** (`:818-819`), so a
`class` declaration in a branch never taken is never reported.

### 3.2 The security model

Global scope is an explicit allowlist of ~30 bindings built in the constructor
(`runtime.ts:617-660`): `tools`, `Promise`, `Object`, `Math`, `JSON`, `Number`,
`String`, `Boolean`, `Array`, `console`, `parseInt`, `parseFloat`, `Date`,
`RegExp`, `Map`, `Set`, `URL`, `URLSearchParams`, URI helpers, Error
constructors. `process` is not among them; the test `return process.env` fails
with a `ReferenceError`
(`packages/opencode/test/tool/code-mode.test.ts:598-602`).

Plus:

- Per-type **method allowlists** (`src/stdlib/collections.ts`,
  `stdlib/string.ts`, …), not arbitrary property dispatch.
- `__proto__` / `constructor` / `prototype` blocked
  (`src/tool-runtime.ts:152-154`).
- A **plain-data copy boundary** in and out of every tool call
  (`copyIn`/`copyOut`, `tool-runtime.ts:171, 297`): rejects non-plain
  prototypes, cycles, depth > 32, and un-awaited promises; copies into
  null-prototype objects.
- Tool-call concurrency capped at 8 via `Semaphore` (`runtime.ts:628`).
- Timeout via `Effect.timeoutOrElse`; because the interpreter yields
  cooperatively, the timeout also interrupts pure busy loops (`:3381`, test at
  `test/codemode.test.ts:1144`).
- **Host path redaction** on every model-visible string (`runtime.ts:151-152`).

What does **not** exist: memory limits, separate heap, CPU/instruction budget.
Regexes run on the host engine, so ReDoS is bounded only by the timeout.

### 3.3 The typed API the model writes against

Signatures are _rendered_ TypeScript strings, not compiled types
(`src/tool-schema.ts`):

```ts
signature: `${toolExpression(path)}(input: ${inputTypeScript(definition, true)}): Promise<${outputTypeScript(definition, true)}>`
```

(`src/tool-runtime.ts:329-333`)

Producing, verbatim from the tests:

```
tools.weather.current(input: {
  city: string,
}): Promise<{
  tempC: number,
}>
```

(`packages/opencode/test/tool/code-mode.test.ts:134-136`)

**Critical caveat for us:** JSON Schemas are render-only. `src/tool.ts:5-8` —
"used to generate the model-visible TypeScript signature only - CodeMode
performs no validation against it." Only Effect Schemas validate. Since OpenCode
passes raw MCP `inputSchema` through as JSON Schema
(`packages/opencode/src/tool/code-mode.ts:126-127`), **MCP tool inputs in
codemode are never schema-validated** — they only cross the plain-data copy.

### 3.4 The catalog is token-budgeted

The generated prompt (`tool-runtime.ts:495-648`) has a **2000-estimated-token
default budget** (`:86`) and selects tools **round-robin across namespaces,
cheapest-first**, so one large MCP server can't starve the others (`:517-539`).
Every namespace always appears with its tool count even at budget zero
(`:623-635`), and when the catalog is partial it advertises
`tools.$codemode.search({ query })` for discovery (`:637-639`). Search scoring
is deterministic and additive: exact path 20, path substring 8, description
substring 4 (`:414-437`).

This is the answer to "MCP tool-list bloat" and it's the part I'd copy nearly
verbatim.

### 3.5 Wiring: MCP-only, env-flag-gated, and it _replaces_ the tools

- Built from `mcp.tools()` grouped by server name
  (`packages/opencode/src/tool/code-mode.ts:210-212`). Native tools
  (read/edit/bash/…) stay as normal tools and are **not** reachable from inside.
- Flag is env-var only: `OPENCODE_EXPERIMENTAL_CODE_MODE`
  (`packages/opencode/src/effect/runtime-flags.ts:48`). No `opencode.json` key.
- When on, `packages/opencode/src/session/tools.ts:388` **early-returns before
  registering the flattened per-MCP-tool wrappers** — so it is N tools → 1
  `execute` tool, a swap not an addition.
- The catalog is regenerated **per model step** against the current permission
  ruleset, and the `execute` tool is dropped entirely if zero MCP tools are
  visible (`packages/opencode/src/tool/registry.ts:275-284, 300-324`).
- Permission is enforced per _nested_ call:
  `ctx.ask({ permission: entry.key, ... })` (`code-mode.ts:147`).

### 3.6 Effect usage

Idiomatic in the small, absent in the large. The `R` channel is genuinely
threaded — `Services<Tools>` (`src/tool-runtime.ts:30-45`) is a recursive
conditional type inferring the service-requirement union from the tool tree, and
`execute` returns `Effect<Result, never, Services<Tools>>`
(`src/codemode.ts:139`). Errors are `never`; the `Result` is data.

But grepping `src/` for `Layer.`, `Context.`, `Effect.Service` returns **zero
hits** — the package defines no services and no layers. It is a pure function
library over Effect values. For a host-neutral library that is arguably correct.

### 3.7 Test ratio

~4700 lines of tests against ~2900 lines of source. `test/parity.test.ts` is a
labeled list of hypotheses H1–H6 about where the interpreter must match real JS
semantics. There is **no fuzzing against a real JS engine** — parity is
hand-curated.

## 4. Client / server / SDK split

### 4.1 The pattern worth stealing outright

One `HttpApi` contract, two transports, **one generated client**:

```ts
const web = HttpRouter.toWebHandler(createEmbeddedRoutes()...)
const fetch = (input, init) => web.handler(new Request(input, init))
const client = yield* OpenCode.make({ baseUrl: "http://opencode.local" }).pipe(
  Effect.provide(FetchHttpClient.layer),
  Effect.provideService(FetchHttpClient.Fetch, fetch))
```

(`packages/sdk-next/src/opencode.ts:20-38`)

The real router is turned into a `fetch` and injected as the HttpClient
transport. No socket, no port, no separate embedded API. **This eliminates the
"library API vs server API" fork entirely** — the exact problem a harness-as-SDK
has to solve.

### 4.2 The layers

- **`packages/protocol`** — pure `HttpApi` definition over Effect Schema, deps
  are only `@opencode-ai/schema` and `effect`. 18 endpoint groups
  (`src/api.ts:38-55`). Errors are schema-tagged with status baked in:
  `Schema.TaggedErrorClass<ConflictError>()("ConflictError", {...}, { httpApiStatus: 409 })`
  (`src/errors.ts:3-42`). The API is a _function_ of middleware keys so protocol
  owns placement and server injects identities (`api.ts:25, 37-64`).
- **`packages/server`** —
  `HttpApiBuilder.layer(Api, { openapiPath: "/openapi.json" })` with a handler
  layer stack (`src/routes.ts:54-62`). **No Hono** anywhere in the server path.
  Two entry points: `createRoutes(password?)` and `createEmbeddedRoutes()` (auth
  disabled).
- **`packages/client`** — generated from the same contract by
  `packages/httpapi-codegen`, in _two_ flavors: a zero-Effect Promise/fetch
  client and an Effect `HttpApiClient` one (`script/build.ts:7-30`). `effect` is
  an optional peer dep so the Promise build stays Effect-free. CI gate:
  `"check:generated": "bun run generate && git diff --exit-code"`
  (`package.json:13`).
- **`packages/sdk`** — generated by `@hey-api/openapi-ts` from OpenAPI derived
  from the same `HttpApi`. It still backs the TUI and both CLIs. Its build
  script carries **three regex post-patches that `throw` if they fail to match**
  (`packages/sdk/js/script/build.ts:74-113`) — a concrete, ongoing tax on the
  OpenAPI round-trip.
- **`packages/sdk-next`** — the Effect replacement, explicitly transitional
  (`README.md:3-5`).

### 4.3 Wire protocol

**HTTP + SSE.** Not JSON-RPC, not websockets (except PTY,
`packages/protocol/src/groups/pty.ts:119-140`).

```ts
HttpApiEndpoint.get("event.subscribe", "/api/event", {
  success: HttpApiSchema.StreamSse({ data: EventSchema })
})
```

(`packages/protocol/src/groups/event.ts:35-37`)

The handler emits a synthetic `server.connected` first, subscribes with a
**bounded dropping queue that fails with `SubscriberOverflowError` rather than
backpressuring the bus** (`packages/core/src/event.ts:152-163`), merges a 15s
heartbeat comment stream, and sets `X-Accel-Buffering: no`
(`packages/server/src/handlers/event.ts:20-48`).

The TUI subscribes at `packages/tui/src/context/sdk.tsx:82-117` with its own
reconnect backoff (1s → 30s) and a 16ms coalescing batch into a Solid `batch()`.
When embedded, it takes an injected `EventSource` and skips SSE entirely
(`sdk.tsx:119-131`).

### 4.4 Auth

HTTP **Basic**, opt-in, off by default (`packages/server/src/auth.ts:25-57`).
Credentials accepted from the `Authorization` header _or_ an `?auth_token=`
query param for EventSource cases
(`packages/server/src/middleware/authorization.ts:9, 29-36`). Embedded routes
hard-code no password. `packages/identity` is brand SVGs, not auth.

## 5. Edit application

### 5.1 Formats

Three, gated by model family (`packages/opencode/src/tool/registry.ts:292-295`):
GPT-5-class models get **only** `apply_patch` (OpenAI envelope diff); everyone
else gets `edit` + `write` and never sees `apply_patch`.

```ts
export const Parameters = Schema.Struct({
  filePath: Schema.String.annotate({
    description: "The absolute path to the file to modify"
  }),
  oldString: Schema.String.annotate({ description: "The text to replace" }),
  newString: Schema.String.annotate({
    description:
      "The text to replace it with (must be different from oldString)"
  }),
  replaceAll: Schema.optional(Schema.Boolean).annotate({
    description: "Replace all occurrences of oldString (default false)"
  })
})
```

(`packages/opencode/src/tool/edit.ts:47-56`; `oldString === ""` means
create-new-file, `:90-96`)

### 5.2 The replacer cascade (`packages/opencode/src/tool/edit.ts:217-737`)

Ported from cline's diff-apply evals and gemini-cli's editCorrector
(`edit.ts:1-4`).

```ts
export type Replacer = (
  content: string,
  find: string
) => Generator<string, void, unknown>
```

Each replacer **yields candidate literal substrings of the file** — it never
rewrites. The driver locates each candidate with `indexOf` and decides. Order
(`edit.ts:682-690`):

1. **`SimpleReplacer`** (`:244`) — yields `find` unchanged; exact match.
2. **`LineTrimmedReplacer`** (`:248`) — line-by-line comparison after `.trim()`;
   reconstructs exact offsets and yields the _untrimmed_ slice. Yields every
   matching window.
3. **`BlockAnchorReplacer`** (`:288`) — needs ≥3 lines. First and last trimmed
   lines are anchors; candidate blocks must be within ±25% of the expected line
   count; middle lines scored by **normalized Levenshtein similarity** against a
   0.65 threshold. With multiple candidates it yields only the single
   best-scoring block — it resolves ambiguity internally.
4. **`WhitespaceNormalizedReplacer`** (`:427`) — `\s+ → " "`; for partial
   single-line matches it rebuilds a `\s+`-joined regex from the find's words to
   recover the exact substring.
5. **`IndentationFlexibleReplacer`** (`:471`) — dedents both sides by their
   minimum common leading whitespace before comparing.
6. **`EscapeNormalizedReplacer`** (`:499`) — decodes `\n \t \r \' \" \` \\ \$`
   for models that emit over-escaped literals.
7. **`TrimmedBoundaryReplacer`** (`:562`) — handles stray leading/trailing blank
   lines.
8. **`ContextAwareReplacer`** (`:588`) — anchors like #3 but requires **exact
   line count match** and ≥50% of non-empty middle lines matching when trimmed.
9. **`MultiOccurrenceReplacer`** (`:548`) — yields exact `find` once per
   occurrence; exists so `replaceAll: true` can fire on genuinely repeated text.

**Ambiguity is not first-match-wins.** A candidate is accepted only if
`content.indexOf(search) === content.lastIndexOf(search)` — globally unique. A
non-unique candidate is _skipped_ and the cascade continues (`edit.ts:717-718`).
Two distinct terminal errors: nothing ever found vs. found-but-always-ambiguous
(`:723-728`).

**The guard rail worth copying** — `isDisproportionateMatch` (`:731-737`) throws
_hard_ (aborting the whole cascade, not skipping) when the fuzzy-matched span is
much larger than what the model asked for:
`searchLines >= max(oldLines+3, oldLines*2)`, or trimmed length
`> max(oldLen + 500, oldLen * 4)`. Without this, fuzzy matching silently eats
hundreds of lines.

`apply_patch` has its own separate 4-pass ladder
(`packages/opencode/src/patch/index.ts:460-484`): exact → rstrip → trim →
Unicode-normalized (smart quotes, en/em dashes, NBSP, ellipsis).

**There is no LLM-based fast-apply.** No morph, relace, or fastapply integration
— grep returns only `morphdom` (DOM diffing) and Morph as a chat _provider_ in a
test fixture.

### 5.3 Around the edit

- Per-path `Semaphore` serializes concurrent edits to one file
  (`edit.ts:35-45, 88`).
- Formatter runs inside the lock, and **the diff is recomputed after
  formatting** (`edit.ts:156-171`).
- **LSP diagnostics are appended to the tool result** — `lsp.touchFile` then
  `"\n\nLSP errors detected in this file, please fix:\n" + block`
  (`edit.ts:196-201`). `write` additionally reports other files' errors, capped
  at 5 files (`write.ts:18, 74-90`). Formatting: severity-1 only, max 20 per
  file, wrapped in `<diagnostics file="...">`
  (`packages/opencode/src/lsp/diagnostic.ts:3-27`).
- Diffs are jsdiff `createTwoFilesPatch` + `diffLines`, with `trimDiff`
  stripping common indentation for display (`edit.ts:646-680`).
- **The documented read-before-write invariant is not implemented in V1.**
  `edit.txt:4` claims "This tool will error if you attempt an edit without
  reading the file", but no `FileTime` / `lastRead` / read-registry state exists
  anywhere. V2 replaces it with something better — optimistic concurrency:
  `files.writeIfUnchanged({ target, expected: source.content, content })`
  failing with `StaleContentError`
  (`packages/core/src/tool/edit.ts:110-119, 191-197`).

### 5.4 Tool definition interface

V1 (`packages/opencode/src/tool/tool.ts:56-68`) —
`{ id, description, parameters: Schema, execute(args, ctx): Effect<ExecuteResult> }`,
with `ctx` carrying `sessionID`, `messageID`, `agent`, `abort`, `callID`, plus
Effect-returning `metadata()` (streaming UI updates) and `ask()` (permission).
Descriptions are sibling `.txt` files imported via Bun's text loader
(`import DESCRIPTION from "./edit.txt"`).

V2 (`packages/core/src/tool/tool.ts:39-64`) —
`Tool.make({ description, input, output, structured?, execute, toModelOutput? })`
where `execute` returns `Effect<Type<Output>, ToolFailure>`. Differences that
matter: **a typed output schema** advertised as JSON Schema, a separate
`toModelOutput` step, errors as a typed channel rather than `Effect.orDie`,
permission attached declaratively by wrapping
(`Tool.withPermission(Tool.make({...}), "edit")`), and descriptions inline
instead of in `.txt` files.

## 6. Context management and persistence

### 6.1 Compaction

`packages/core/src/session/compaction.ts` — 241 lines, the whole mechanism. Two
triggers:

- **Proactive:**
  `estimate(system + messages + tools) > contextWindow - max(maxOutputTokens, buffer)`
  where `buffer` defaults to **20,000 tokens** (`:12, 230-234`).
- **Reactive:** on a provider context-overflow error, _only if no assistant text
  has started_ (`packages/core/src/session/runner/llm.ts:283-288`).

`select()` walks messages **backwards** accumulating tokens until it exceeds
`keep.tokens` (default 8,000, `:13`); the newer half is kept **verbatim as
serialized text**, the older half is summarized (`:128-159`). Tool outputs are
truncated to 2,000 chars during serialization (`:14`). The prompt is a template
literal (`SUMMARY_TEMPLATE`, `:16-46`) requiring exact Markdown sections:
Objective / Important Details / Work State (Completed, Active, Blocked) / Next
Move / Relevant Files.

The result becomes a `compaction`-typed message, and history loading **drops
everything before it** (`packages/core/src/session/history.ts:13-43`). It is
re-rendered to the model as a _user_ message wrapped in
`<conversation-checkpoint>` with `<summary>` and `<recent-context>`
(`runner/to-llm-message.ts:147-165`).

**Three defects worth knowing:**

1. Budgeting uses `JSON.stringify(...).length / 4`
   (`packages/core/src/util/token.ts:3-5`), while accurate provider usage _is_
   captured and persisted (`runner/publish-llm-event.ts:18-25`) but never fed
   back. The 20k buffer absorbs the error.
2. The summarizer runs with **no system prompt** (`compaction.ts:196-203`),
   despite `PROMPT_COMPACTION` existing at
   `packages/core/src/plugin/agent.ts:33-41` bound to a hidden agent that
   nothing in V2 references.
3. Manual `/compact` is stubbed: `OperationUnavailableError`
   (`session.ts:417-419`).

### 6.2 Prompt caching

Two layers. **Policy** (`packages/llm/src/cache-policy.ts`): default `"auto"`
places exactly **3 breakpoints** — last tool definition, last system part, last
text part of the latest user message (`:18-22, 47-97`). Applied only for
protocols honoring inline markers (`anthropic-messages`, `bedrock-converse`,
`:42`); OpenAI/Gemini skipped in favor of implicit prefix caching. **Wire
lowering** (`packages/llm/src/protocols/anthropic-messages.ts:238-251`): cap of
4 breakpoints with a decrementing counter; excess markers are **silently
dropped**. The auto-policy's 3 leaves exactly one for manual hints.

For OpenAI they set a stable `promptCacheKey` derived from the session id
(`runner/llm.ts:204-207`).

### 6.3 Persistence

SQLite via drizzle, WAL, at `$XDG_DATA_HOME/opencode/opencode.db`
(`packages/core/src/database/database.ts:27-55`). **Event-sourced with
projections**: an `event`/`event_sequence` log
(`packages/core/src/event/sql.ts:4-25`) plus projected tables.

`session_message` (`packages/core/src/session/sql.ts:119-138`) is **one row per
message with a JSON blob body** and a monotonic `seq` unique per session. There
is no separate part table in V2 — assistant parts live inside `data.content[]`.
Message union (`packages/schema/src/session-message.ts:200-213`):
`agent-switched | model-switched | user | synthetic | system | shell | assistant | compaction`.
Assistant content parts: `text | reasoning | tool`, with tool state a 4-way
union `pending → running → completed | error` (`:82-119`).

Migrations are **TypeScript modules `{id, up(tx)}`** statically listed in a
generated file (`packages/core/src/database/migration.gen.ts`, ~46 entries),
with a raw-SQL baseline for fresh databases (`schema.gen.ts`) and a serializing
`Semaphore(1)` (`migration.ts:11, 19`).

`packages/effect-drizzle-sqlite` is a **vendored fork of drizzle's unreleased
Effect adapter**, explicitly marked for deletion when upstream ships
(`AGENTS.md:9-10`). It defines no service tag; the consumer does
(`packages/core/src/database/database.ts:13-37`). Don't copy the package; copy
the _pattern_ (`Context.Service` wrapping a drizzle handle, `layerFromPath`,
pragmas + migrations inside `Layer.effect`, platform-conditional `#sqlite`
import). `packages/effect-sqlite-node/src/index.ts` (50 lines, `node:sqlite` →
Effect `SqlClient`) is a clean standalone copy candidate.

### 6.4 Snapshots and revert

Snapshots use a **shadow git repo with GIT_DIR outside the user's repo**:
`$XDG_DATA_HOME/opencode/snapshot/<projectID>/<hash>` pointing at the user's
worktree (`packages/core/src/snapshot.ts:98, 109-119`). The user's own `.git` is
never touched. Best-effort — returns `ID | undefined` (`:44-49`). Captured at
turn start and end (`runner/llm.ts:217, 318-324`).

Revert is 3-phase — `plan` / `stage` (reversible preview) / `commit` — and a
committed revert **deletes all messages after the boundary** and resets the
context epoch (`packages/core/src/session/revert.ts`, `projector.ts:415-454`).
There is **no session forking/branching**: `parent_id` models subagent
parentage, not conversation forks.

### 6.5 System prompt assembly

Only `AGENTS.md` — walked upward from cwd to project root, prefixed with the
global `$XDG_CONFIG_HOME/opencode/AGENTS.md`, deduped
(`packages/core/src/instruction-context.ts:40-74`). No
`CLAUDE.md`/`.cursorrules` fallback in V2. If a discovered file fails to read,
the source returns `unavailable` rather than silently building a partial prompt
(`:71-72`).

Sources are composable and individually refreshable
(`packages/core/src/system-context/index.ts:32-39`): `core/environment`,
`core/date`, `core/instructions`, `core/skill-guidance`,
`core/reference-guidance`. The final system prompt is **exactly two parts**:
`[agent.info?.system, system.baseline]` (`runner/llm.ts:208-210`). No
per-provider prompt variation in V2.

The **context epoch** (`packages/core/src/session/context-epoch.ts`) is the
clever bit: the rendered baseline is pinned at a sequence number, and
mid-session changes are injected as a `system` _message_ delta rather than
rewriting the baseline — which keeps the cached prefix stable. History loading
skips `system` messages already folded into the baseline (`history.ts:44-47`).

## 7. Permission / approval

The core primitive is a **`Deferred` in a pending map with a scope finalizer**:

```ts
const deferred = Deferred.makeUnsafe<void, RejectedError | CorrectedError>()
pending.set(id, { info, deferred })
yield * events.publish("permission.asked", info)
return (
  yield *
  Deferred.await(deferred).pipe(
    Effect.ensuring(Effect.sync(() => pending.delete(id)))
  )
)
```

(`packages/opencode/src/permission/index.ts:98-106`; a finalizer fails every
outstanding Deferred on teardown, `:54-61`, so a dying instance never leaks a
hung tool.)

V2 refines this in two ways worth copying
(`packages/core/src/permission.ts:190-218`): `ask` (non-blocking, returns the
verdict) is split from `assert` (blocking), and `assert` wraps in
`uninterruptibleMask` with `restore` **only around the `Deferred.await`**, so
registration/publish can't be interrupted mid-flight.

Config: a permission value is `"ask" | "allow" | "deny"` or a
`Record<pattern, action>` (`packages/core/src/v1/config/permission.ts:5-8`).
Known keys include
`read, edit, glob, grep, bash, task, external_directory, webfetch, websearch, skill`,
plus an open record so MCP tool names work (`:18-35`). **Key order is
load-bearing** — parsing uses `propertyOrder: "original"` and `findLast` wins
(`:14-16`, `permission/index.ts:32`). A `deny` with pattern `*` also **hides the
tool from the model entirely** (`:204-219`).

The **best idea here** is two-tier pattern matching for bash. Commands are
parsed with **tree-sitter-bash and tree-sitter-powershell WASM grammars**
(`packages/opencode/src/tool/shell.ts:309-330`), and
`root.descendantsOfType("command")` (`:123-124`) extracts every command
including those inside pipes, `&&`, and subshells. Then:

- The _ask_ uses the literal command source text (`:408`).
- The _"always allow"_ uses an **arity-generalized prefix** (`:409`) —
  `BashArity.prefix` with a dictionary of command → meaningful-token-count
  (`packages/opencode/src/permission/arity.ts`), so approving
  `git commit -m foo` grants `git commit *`, not `git *` and not the exact
  string. This pairs with a special case in the wildcard matcher where a pattern
  ending `" .*"` becomes `"( .*)?"` so bare `git push` still matches
  (`packages/core/src/util/wildcard.ts:10`).

"Always allow" state: V1 in-memory and session-scoped; **V2 persists to SQLite,
per-project** (`packages/core/src/permission/saved.ts:54-70`). V2 also checks
configured `deny` _before_ merging saved allows (`permission.ts:157`), so a
saved allow can never override a config deny.

## 8. MCP support

**Consume-only. OpenCode does not serve MCP** — zero imports of
`@modelcontextprotocol/sdk/server/*`. It exposes itself over HTTP and ACP
instead.

All MCP lives in `packages/opencode/src/mcp/` (1004-line `index.ts`).
**`packages/core` has no MCP module** — V2 has not absorbed it.

**Spec revision:** SDK pinned at `1.29.0`, which implements **2025-11-25** (the
patch context shows `experimental.tasks.callToolStream` and SEP-835 scope
selection; `mcp/index.ts:47-48` has a commented-out `tasks: {}` capability).
Note this is _older_ than our 2026-07-28 stateless target.

**Primitives — definitively:**

| Primitive             | Status                                                                         |
| --------------------- | ------------------------------------------------------------------------------ |
| tools                 | full, with pagination and `list_changed` (`catalog.ts:37`, `index.ts:462-471`) |
| resources + templates | full, exposed as agent tools (`index.ts:720-738`)                              |
| prompts               | full, surfaced as slash commands (`index.ts:716-718`)                          |
| roots                 | implemented — the only server→client primitive (`index.ts:46, 77-79`)          |
| logging               | consumed, bridged into Effect logging (`index.ts:457-490`)                     |
| **sampling**          | **not implemented** — capability deliberately commented out (`index.ts:41-42`) |
| **elicitation**       | **not implemented** — commented out (`index.ts:43-44`)                         |
| **tasks**             | not implemented (`index.ts:47-48`)                                             |
| completions           | no reference anywhere                                                          |

Transports: stdio, streamable HTTP (tried first), SSE (fallback) — with an auth
error breaking out rather than falling back (`index.ts:271-332`). Namespacing is
`sanitize(server) + "_" + sanitize(tool)` where `sanitize` replaces
non-`[A-Za-z0-9_-]` (`catalog.ts:112-114`) — note this is **not injective**;
`a.b` and `a_b` collide silently.

Failure handling is good: servers connect concurrently and independently, a
failure yields `status: failed` without blocking startup (`index.ts:505-529`);
`onclose` drops the tools and publishes `ToolsChanged` so the list shrinks live
(`:443-455`); stdio descendants are reaped via `pgrep -P` BFS (`:418-440`).
Timeout default is **30s** despite the config schema docs saying 5000
(`index.ts:38` vs `packages/core/src/v1/config/mcp.ts:21` — the schema docs are
stale).

OAuth for remote servers is extensive: dynamic client registration, loopback
callback with CSRF state check (`index.ts:824-827, 909-913`), token expiry
tracking, `opencode mcp auth|logout|debug`.

### 8.1 The MCP SDK patch is a bug checklist

`patches/@modelcontextprotocol%2Fsdk@1.29.0.patch` fixes five real client gaps.
Any Effect MCP client we write should handle all of these natively:

1. **Streamable-HTTP session recovery.** A `404` with a session id triggers
   `_recoverSession()` → re-initialize → retry once. The stock SDK dies
   permanently when a server rotates its `Mcp-Session-Id`.
2. **`isJSONRPCErrorResponse` counted as a response** in the SSE replay path —
   stock SDK only set `receivedResponse` for _result_ responses, so a JSON-RPC
   error left the client thinking it must reconnect.
3. **`isRequestActive` callback** threaded into `transport.send()` so a retry
   can be abandoned when the caller already gave up.
4. **`cacheToolMetadata(tools, reset = true)`** — the stock SDK cleared the
   output-validator cache on every pagination page, so after paging only the
   last page had validators.
5. **OAuth `offline_access`** — `scope?.includes(...)` →
   `scope?.split(' ').includes(...)` (substring vs token match), plus appending
   `offline_access` when supported. Without it many providers never issue a
   refresh token.

## 9. Observability

Wired at `packages/core/src/observability.ts:11-22`, construction at
`observability/otlp.ts:55-77`. **Entirely gated on
`OTEL_EXPORTER_OTLP_ENDPOINT`** — absent means `Layer.empty` and the OTel
packages are never even imported (they're dynamic imports, `:57-61`).
`NodeSdk.layer()` + `BatchSpanProcessor` → OTLP HTTP.

**The trap to remember** (`otlp.ts:63-66`): they manually instantiate and
globally register an `AsyncLocalStorageContextManager`, with the comment _"The
Effect Node SDK does not register a global context manager, but the AI SDK uses
it to parent spans."_ Without this, Vercel AI SDK spans orphan from Effect
spans.

**Coverage comes mostly for free from `Effect.fn("Name")`**, which auto-creates
a span. That means the agent loop, LLM calls, tool executions, permission asks,
and MCP connects are all traced without explicit instrumentation. There are 25
additional explicit `Effect.withSpan` sites; `Tool.execute` carries `tool.name`,
`session.id`, `message.id`, `tool.call_id`
(`packages/opencode/src/tool/tool.ts:114-119`).

**They are not GenAI-semconv compliant.** `grep -rn "gen_ai"` across all
`packages/*/src` returns exactly one hit, an unrelated OAuth scope string. LLM
spans come from AI SDK's `experimental_telemetry`
(`packages/opencode/src/session/llm.ts:344-351`), which requires _both_ the OTLP
endpoint **and** a config flag `experimental.openTelemetry`. OpenCode's own
attributes are a parallel non-standard namespace (`session.id`, `tool.name`,
`tool.call_id`).

**No metrics at all** — zero `Metric.` / `MeterProvider` references. Logs do go
to OTLP (`OtlpLogger.make({ url: ${endpoint}/v1/logs })`, `otlp.ts:50-53`).
Effect logging is replaced wholesale (`mergeWithExisting: false`) with a logfmt
formatter writing to a rolling file, so nothing leaks to stdout and corrupts the
TUI (`observability/logging.ts:6-52`, `observability.ts:13`).

## 10. Conclusions

### (a) What we should reuse as template

**Tier 1 — copy the design, near-verbatim:**

1. **The one-contract-two-transports pattern.** `HttpApi` →
   `HttpRouter.toWebHandler` → inject as `FetchHttpClient.Fetch` → the _same
   generated client_ works in-process and over the network
   (`packages/sdk-next/src/opencode.ts:20-38`). This is the single best idea in
   the repo and it directly solves harness-as-SDK-and-CLI.
2. **Codemode's token-budgeted catalog with round-robin namespace fairness +
   `$codemode.search` discovery**
   (`packages/codemode/src/tool-runtime.ts:495-648`). This is the answer to MCP
   tool-list bloat, and it's the piece most aligned with our tool-factory
   thesis.
3. **Durable steering via a `session_input` table with `steer | queue`
   delivery** (`packages/core/src/session/input.ts`, `sql.ts:140-166`) plus the
   **coalescing per-key run coordinator** (`run-coordinator.ts`, 104 lines —
   read it, it's small and complete).
4. **`Deferred`-based permission suspension** with the V2 refinements: `ask` vs
   `assert` split, and `uninterruptibleMask` restoring only around the await
   (`packages/core/src/permission.ts:190-218`).
5. **Two-tier bash permission matching** — literal text for the ask,
   arity-generalized prefix for "always"
   (`packages/opencode/src/tool/shell.ts:408-409` + `permission/arity.ts`).
6. **Shadow-git snapshots** with GIT_DIR outside the user's repo
   (`packages/core/src/snapshot.ts:98`). This is the cheapest possible
   checkpoint mechanism and it never touches the user's index.
7. **`isDisproportionateMatch`** as a hard abort on fuzzy edit matching
   (`edit.ts:731-737`). Whatever edit format we choose, we need this guard.

**Tier 2 — copy the mechanism:**

8. The **codegen-with-CI-diff-gate** pattern: `compile → emit → write`, output
   committed, CI runs `git diff --exit-code`
   (`packages/client/package.json:13`).
9. The **context epoch**: pin the rendered system baseline at a sequence number
   and inject changes as delta messages rather than rewriting the prefix
   (`packages/core/src/session/context-epoch.ts`). This is what makes prompt
   caching survive a long session.
10. **`Effect.fn("Name")` as the tracing strategy** — near-total span coverage
    for free.
11. `packages/effect-sqlite-node/src/index.ts` (50 lines) as a clean
    `node:sqlite` → Effect `SqlClient` starting point, and the
    `Context.Service`-wrapping-drizzle pattern from
    `packages/core/src/database/database.ts:13-37`.

**Tier 3 — read for reference, don't copy:**

12. The 9-replacer cascade. It is excellent work, but it is 500 lines of
    heuristics compensating for a weak model's inability to reproduce exact
    strings. See (b).
13. `LayerNode` (333 lines). Only worth it if we need per-location service
    subgraphs in one process.

### (b) What we should deliberately do differently

1. **Our verification harness should make the replacer cascade unnecessary, not
   reimplement it.** OpenCode's cascade exists because a single edit attempt
   must succeed or the turn is wasted. Our thesis is best-of-N rollouts with
   deterministic verification: an edit that fails to apply is a _cheap,
   instantly-detected_ failed rollout. Start with exact-match-or-fail (what V2
   itself does — `packages/core/src/tool/edit.ts:84`), keep
   `isDisproportionateMatch`, and let N-sampling absorb the miss rate. Revisit
   only if measurement shows edit-apply failures dominating the rollout budget.

2. **Code-mode should be the default for MCP, not an env-flag experiment.**
   OpenCode gates it behind `OPENCODE_EXPERIMENTAL_CODE_MODE` and it swaps out
   MCP tools only. For a model weak at long-horizon tool orchestration, the
   value of code-mode is _exactly_ that it collapses a 10-step tool sequence
   into one authored program — the harness carries the sequencing. That is our
   thesis. It should be the primary path, and it should cover native tools too,
   not just MCP.

3. **Validate tool inputs.** OpenCode's codemode explicitly does not validate
   JSON Schema (`packages/codemode/src/tool.ts:5-8`), so MCP tool inputs cross
   the boundary unchecked. With MCP-native as a core claim, we must decode JSON
   Schema into Effect Schema (or reject servers whose schemas we can't) and
   validate at the boundary.

4. **Real token counts, not `length / 4`.** OpenCode captures accurate provider
   usage and then budgets with `JSON.stringify(...).length / 4` anyway
   (`packages/core/src/util/token.ts:5`). For a cheap model where we can afford
   more turns, mis-budgeting is more expensive, not less. Feed the last observed
   usage back into the threshold.

5. **Emit `gen_ai.*` semantic conventions from day one.** OpenCode emits a
   private namespace and delegates LLM spans entirely to AI SDK. Since we're
   targeting LangSmith-via-OTel, GenAI semconv compliance on model and tool
   spans is a first-class requirement, not a later cleanup. This is a place
   where we can be strictly ahead.

6. **Own the provider client — and note that OpenCode reached the same
   conclusion.** V1 uses Vercel AI SDK; V2 replaced it with `packages/llm`,
   ~5700 lines of direct protocol implementations (`anthropic-messages`,
   `openai-chat`, `openai-responses`, `gemini`, `bedrock-converse`) returning
   `Stream<LLMEvent, LLMError>`. For a Mercury-2-first harness with one primary
   provider, a thin Effect `HttpClient` + `Stream` protocol client is the right
   amount of code, and it removes the AsyncLocalStorage span-parenting hack (§9)
   entirely.

7. **Don't use defects as control flow.** The compaction re-entry via
   `TurnTransitionError` thrown as a defect (`runner/llm.ts:152-166`) hides a
   legal outcome from the type signature. Return a `Turn.Result | Turn.Restart`
   union instead.

8. **Sub-agents belong in the loop from the start, not bolted on.** Our
   best-of-N thesis makes parallel rollouts the _primary_ execution mode.
   OpenCode's `task` tool is V1-only, depth-capped at 1 by default, and V2
   hasn't ported it. We should design the loop around fan-out (`FiberSet` per
   rollout, deterministic verifier as the selector) rather than treating a
   subagent as a special tool.

9. **Target the current MCP spec.** OpenCode is on 2025-11-25 and consumes
   tools/resources/ prompts/roots/logging. We're targeting the 2026-07-28
   stateless revision, and _elicitation_ in particular — which OpenCode
   deliberately left unimplemented — maps directly onto the permission
   `Deferred` primitive they already have. That's a differentiator available
   cheaply.

### (c) Traps

1. **Effect 4 is beta and you will patch it.**
   `patches/effect@4.0.0-beta.83.patch` fixes `HttpApiSchema.StreamSse`'s
   OpenAPI identifier collision. Budget for pinning an exact beta and carrying
   patches. Do not use `^`.

2. **The OpenAPI round-trip is a tax.** `packages/sdk/js/script/build.ts:74-113`
   carries three regex post-patches that `throw` if they stop matching — the
   price of `HttpApi → OpenAPI → hey-api`. Generating the Effect client
   _directly_ from `HttpApi` (their `packages/client` path) avoids all of it. If
   we need a non-Effect client, emit it from the same contract, not from
   OpenAPI.

3. **`Effect.fn` naming is load-bearing for observability.** Because spans come
   from function names, an unnamed `Effect.fn` or a plain `Effect.gen` is an
   invisible hole in the trace. This needs to be a lint rule, not a convention.

4. **`AsyncLocalStorageContextManager` must be registered manually** if any
   third-party OTel- instrumented library sits under Effect (`otlp.ts:63-66`).
   Silent orphaned spans otherwise.

5. **Stale prose in tool descriptions is a real bug class.** `edit.txt:4`
   promises an error that the code never raises; `config/mcp.ts:21` documents a
   5s timeout where the code uses 30s. Descriptions are part of the prompt —
   they need the same review bar as code.

6. **Non-injective MCP tool-name sanitization** (`catalog.ts:112-114`) silently
   overwrites colliding tools in a plain record. Use a collision-detecting map.

7. **SSE subscribers drop rather than backpressure**
   (`packages/core/src/event.ts:152-163`, bounded 256, fails with
   `SubscriberOverflowError`). This is the right call for a UI, but a
   _tracing/eval_ consumer that silently loses events is a correctness bug. Our
   eval pipeline should read the durable event log, not the live stream.

8. **Anthropic cache breakpoints beyond 4 are silently dropped**
   (`anthropic-messages.ts:246-248` increments a `dropped` counter nothing
   surfaces). Surface it.

9. **Codemode has no memory or CPU budget** — only a wall-clock timeout, and
   regexes run on the host engine. Acceptable for a local CLI; not acceptable if
   the harness ever runs untrusted model output in a shared process.

10. **Half-finished migrations are the repo's dominant hazard.** V2 is missing
    MCP, sub-agents, tree-sitter bash permissions, fuzzy edit repair, and manual
    compaction. Anything you copy from `packages/core` may be a stub; anything
    you copy from `packages/opencode` may be the version they decided was wrong.
    Always check both.
